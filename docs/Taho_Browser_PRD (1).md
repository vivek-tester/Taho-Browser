# Taho Browser — Product Requirements Document

**Product:** Taho Browser  
**Companion Product:** Taho API Testing  
**Platform:** Android  
**Browser Engine:** Mozilla GeckoView  
**Core UX Principle:** **Browser First, Tools Second**  
**Status:** Product and architecture baseline  
**Date:** 2026-09-26

---

## 1. Executive Summary

Taho Browser is an Android-first technical browser built on **GeckoView**. Its primary purpose is to provide a fast, usable browser while allowing network and web-runtime observation to operate in the background.

Taho Browser must **not become a permanent developer dashboard**. Browsing remains the primary activity; technical tooling appears progressively when the user asks for it or when relevant captured activity exists.

The central product loop is:

> **Browse naturally → observe relevant traffic → inspect when needed → transfer a request into Taho API Testing → modify, test, replay, and save.**

The integration between Taho Browser and Taho API Testing is therefore a core product boundary rather than a generic export feature.

A user who discovers a request while interacting with a website should not have to:

- copy cURL manually,
- reconstruct headers,
- remove browser-only headers,
- copy JSON by hand,
- recreate authentication,
- save an intermediate file,
- or switch repeatedly between tools.

Instead:

> **A captured request should become a native, editable Taho request through one explicit and understandable handoff.**

The architecture is constrained by GeckoView's capabilities. Taho Browser observes traffic generated by its own GeckoView sessions, uses WebExtension/native messaging for observation, and does not depend on device-wide VPN interception or user-installed CA certificates.

# 2. Product Vision

### Vision

Create a coherent Android workflow that allows a developer, QA engineer, or security researcher to move from a real web interaction to an editable and testable API request without requiring desktop DevTools or manual request reconstruction.

### Product statement

> **Taho Browser lets you browse normally and turn the relevant network interaction into a Taho API test when you need it.**

### Core doctrine

**Browser First, Tools Second**

1. Browsing is the primary activity.
2. Capture is ambient.
3. Technical information is progressively disclosed.
4. Relevant traffic is surfaced instead of overwhelming the user with network noise.
5. Inspection is contextual.
6. Transfer to Taho is explicit and reversible.
7. Taho API Testing becomes the deep testing workspace.
8. Taho Browser does not attempt to become a complete API client.

---

# 3. Problem Statement

Mobile API investigation commonly requires:

- desktop browser DevTools,
- ADB/USB workflows,
- proxy configuration,
- certificate installation,
- manual cURL extraction,
- copy/paste,
- removal of browser-specific headers,
- manual reconstruction of request bodies,
- separate authentication handling,
- switching between applications.

These workflows introduce friction and create opportunities for incorrect requests or credential leakage.

The desired workflow is:

```text
Open web application
        ↓
Interact normally
        ↓
Taho observes relevant traffic
        ↓
Identify API request
        ↓
Inspect
        ↓
Send to Taho
        ↓
Edit / test / save
```

The user should not need to understand how GeckoView, WebExtensions, native messaging, Room, or Android IPC work.

# 4. Goals

## 4.1 Primary goals

- Build Taho Browser on GeckoView.
- Keep browsing as the dominant interaction.
- Observe relevant network activity generated by Taho Browser.
- Correctly attribute captured events to their originating browser session.
- Normalize captured requests for API testing.
- Provide secure native transfer to Taho API Testing.
- Preserve request provenance.
- Mask sensitive values by default.
- Allow explicit user-controlled credential transfer when required.
- Support single-request transfer as the first integration milestone.
- Keep the normal handoff local to the device.
- Clearly communicate capture limitations and incomplete data.

## 4.2 Secondary goals

- Batch request transfer.
- Environment-variable parameterization.
- Response/timing/security metadata transfer.
- Large-payload transfer.
- Browser-session/workflow transfer.
- Future WebSocket workspace integration.

---

# 5. Non-Goals

Taho Browser is not intended to become:

- a desktop DevTools clone,
- a system-wide packet sniffer,
- a VPN capture engine,
- a TLS interception proxy,
- a Burp/Charles/mitmproxy replacement,
- a complete HAR archive in the initial release,
- a full raw WebSocket forensic tool,
- a cloud traffic collection service,
- a permanent network log.

The browser should not expose technical controls merely because the underlying engine can expose technical information.

# 7. Product Principles

## 7.1 Browser First

The webpage is the primary canvas.

Avoid permanent:

- request tables,
- network timelines,
- developer sidebars,
- floating technical controls.

## 7.2 Ambient Capture

Capture should feel like a background capability.

Example:

```text
● 6 relevant requests
```

rather than:

```text
1,482 packets captured
```

## 7.3 Progressive Disclosure

Four levels:

1. **Ambient** — browser + capture state.
2. **Summary** — relevant requests.
3. **Inspector** — detailed request information.
4. **Fullscreen** — advanced technical tooling.

## 7.4 Relevance Before Volume

Prioritize API and authentication traffic over:

- images,
- fonts,
- CSS,
- trackers,
- analytics,
- telemetry.

## 7.5 Provenance

Every transferred request must retain enough information to establish where it originated:

- source product,
- capture session,
- source tab/session,
- capture timestamp,
- original URL,
- method,
- completeness.

## 7.6 Zero False Confidence

If data is:

- unavailable,
- truncated,
- partial,
- inferred,
- transformed,

the UI must say so.

## 7.7 Credential Defense

Sensitive data must be protected across:

- capture,
- memory,
- UI,
- persistence,
- IPC,
- exports,
- clipboard,
- replay.

## 7.8 Local-First Boundary

Normal Browser → Taho transfer is an on-device operation.

# 9. Core Architectural Layers

## 9.1 Browser Engine Layer

**Required engine:** GeckoView.

Responsibilities:

- rendering,
- GeckoSession lifecycle,
- navigation,
- browser security,
- cookies,
- storage,
- TLS/browser state,
- content blocking.

The browser architecture should isolate engine-specific code from product UI and capture-domain code.

---

## 9.2 Observation Layer

The observation backbone is the built-in WebExtension and GeckoView integration.

The system may observe:

- HTTP request metadata,
- headers,
- request bodies where exposed,
- response metadata,
- logical HTTP/2/HTTP/3 information,
- TLS/security information where available,
- WebSocket handshakes.

Some capabilities are conditional.

### Response bodies

Passive response-body capture is not universally guaranteed. Selective response stream handling must be carefully scoped and must not disrupt page loading.

### WebSocket frames

Post-handshake WebSocket frames are not exposed by the normal webRequest layer. Page instrumentation can provide a higher-level observation mechanism, but it must be labeled as such.

### Raw transport data

The product must not imply access to:

- raw HTTP/2 frames,
- raw QUIC packets,
- arbitrary UDP traffic,
- browser-internal network traffic.

---

# 10. Session and Event Attribution

This is a **P0 correctness requirement**.

A captured event must never be assigned to the currently visible tab merely because that tab is selected.

Incorrect:

```text
Network event
    ↓
Currently selected tab
```

Required:

```text
Network event
    ↓
Originating GeckoSession
    ↓
Taho browser session
    ↓
Capture session
```

Unknown ownership must not silently fall back to the selected session.

The native messaging architecture must preserve the originating GeckoSession/session identity wherever GeckoView exposes it.

---

# 11. Native Messaging Architecture

For high-frequency capture traffic, use a connection-oriented native messaging architecture where supported.

Conceptually:

```text
WebExtension
     │
     │ runtime.connectNative()
     ▼
Native message port
     │
     ▼
Capture Bridge
     │
     ├── CaptureCoordinator
     ├── Storage
     └── UI StateFlow
```

Content-script communication must use the correct session-aware GeckoView delegate path.

Every native message must be:

- schema validated,
- size limited,
- type checked,
- attributed to its originating session,
- treated as untrusted input.

A captured request must have separate representations:

```text

      ↓
NormalizedRequest
      ↓

      ↓

      ↓
```

# 21. Request Normalization

The transfer normalizer should remove browser-generated headers that are generally inappropriate for API testing, where applicable:

- `Host`
- `Content-Length`
- `Sec-Fetch-*`
- `Sec-CH-UA*`
- other transport-generated headers.

Meaningful application headers must remain, including where applicable:

- `Content-Type`
- `Accept`
- `Authorization`
- `X-API-Key`
- `X-CSRF-Token`.

The normalizer must be explicit, versioned, and testable.

# 23. Secret Handling

Support three policies.

## 23.1 Parameterize — default

Example:

```text
Authorization: {{AUTH_TOKEN}}
```

Taho can create or request the corresponding environment variable.

## 23.2 Mask

```text
Authorization: Bearer ••••••••
```

The request is not executable as-is.

## 23.3 Explicit secret transfer

Advanced users may deliberately include captured credentials.

The UI must show:

- which secrets are included,
- category,
- destination app,
- destination host,
- persistence implications.

No secret should be transferred silently.

---

# 24. Recommended Android Handoff

## 24.1 Primary transport: Explicit Intent

For normal request payloads:

```text
Taho Browser
    ↓
User taps Send to Taho
    ↓
Build transfer envelope
    ↓
Explicit Android Intent
    ↓
Taho import entry point
    ↓
Validate
    ↓
Open request editor
```

The Intent should target the known Taho package rather than exposing the request to arbitrary handlers.

---

## 24.2 Large payload transport

Large request bodies should not be forced into Intent extras.

Use:

```text
Capture
   ↓
Secure temporary file
   ↓
Content URI
   ↓
Explicit Intent + URI grant
   ↓
Taho reads and validates
   ↓
Temporary artifact deleted
```

The user should not need to know which transport was selected.

---

## 24.3 Clipboard

Clipboard must not be the normal integration path.

It may remain a manual fallback for cURL or text export.

---

## 24.4 AIDL

AIDL is not required for the initial integration.

It can be reconsidered for a future persistent Browser ↔ Taho workspace service.

---

## 24.5 Public ContentProvider

A general public provider is unnecessary for the MVP.

A protected provider may become appropriate for future persistent shared workspace data.

# 25. Versioned Transfer Envelope

The integration must not directly serialize Taho's internal Dart/Kotlin model.

Use an independent interchange contract.

Example:

```json
{
  "schema": "taho.request-transfer",
  "version": 1,
  "source": {
    "product": "taho-browser",
    "appVersion": "1.0.0",
    "captureSessionId": "session-id",
    "tabId": "tab-id"
  },
  "request": {
    "id": "request-id",
    "method": "POST",
    "url": "https://api.example.com/v1/orders",
    "query": [],
    "headers": [],
    "body": {
      "contentType": "application/json",
      "encoding": "utf-8",
      "content": "..."
    }
  },
  "capture": {
    "timestamp": 0,
    "durationMs": 0,
    "status": 201,
    "completeness": {
      "requestBody": "COMPLETE",
      "responseBody": "UNAVAILABLE"
    }
  },
  "security": {
    "secretPolicy": "PARAMETERIZE",
    "containsSensitiveData": true
  }
}
```

Required compatibility fields:

```text
schema
version
minimumReaderVersion
```

Unknown schemas must fail safely.

# 32. WebSocket and SSE

Do not force these protocols into the ordinary HTTP request-transfer model.

### WebSocket

MVP:

```text
WebSocket handshake
        ↓
Transfer as HTTP upgrade request
```

Future:

```text
WebSocket session
        ↓
Taho WebSocket workspace
```

### SSE

Transfer the initiating HTTP request.

Stream-specific metadata may be retained as provenance.

Do not represent an active long-lived stream as a normal completed response.

# 33. Privacy Boundaries

Taho Browser contains two separate domains.

### Browser data

- cookies,
- history,
- cache,
- site storage,
- browsing state.

### Capture data

- transactions,
- request metadata,
- response metadata,
- inspection history.

They must remain independently clearable.

### Clear browsing data

Must not silently delete capture logs unless the user explicitly selects that option.

### Clear capture data

Must not log the user out of websites.

---

# 34. Private Browsing

Private sessions require an explicit persistence boundary.

If a user sends a private-session request to Taho, the UI should communicate that the request is leaving the private browsing context and may become persistent in Taho.

Recommended behavior:

```text
This request came from a private session.

Sending it to Taho may persist the request there.

[ Continue ] [ Cancel ]
```

---

# 35. Replay Safety

Taho must not blindly replay all captured credentials.

Before execution:

1. classify sensitive headers,
2. mask/strip by default,
3. require explicit inclusion,
4. warn if destination origin changes,
5. show original and new destination.

Example:

```text
Original
api.example.com

New destination
attacker.example

Authorization is present.

[ Cancel ] [ Send Anyway ]
```

This protects against accidental credential exfiltration caused by modifying a captured request.

---

# 36. Content Blocking

Taho Browser should use GeckoView's native content-blocking/tracking-protection capabilities.

The product should not claim to provide a full uBlock-style arbitrary filter-list engine unless such an engine is actually implemented.

Allowlisting must correctly account for every protection layer being applied.

- selection feedback: <100 ms perceived UI response,
- confirmation surface: immediate,
- normal transfer: approximately <1 second perceived completion on a typical device,
- large transfer: progress indication,
- serialization off the UI thread,
- no unbounded capture queue.

The user should not see a blank or frozen browser while a request is being serialized.

The direct Intent path should have a conservative configured payload budget.

Do not depend on a theoretical maximum.

When approaching the configured threshold:

```text
Direct Intent
      ↓
File-backed transfer
```

The transport selection should be automatic.

# 53. Detailed Functional Specification

This section converts the product principles into implementation-level product requirements. It does not replace the GeckoView capability model; it defines how the product should behave within those constraints.

## 53.1 Browser Startup

On startup:

1. Initialize the Gecko runtime.
2. Initialize the capture subsystem independently from UI state.
3. Initialize the built-in WebExtension.
4. Establish the native messaging bridge.
5. Create the initial browser session.
6. Register the session with the capture coordinator.
7. Restore persisted browser/capture state where applicable.
8. Render the browser before exposing technical tooling.

The browser must remain usable if capture initialization fails.

Failure of the capture subsystem must degrade to:

```text
Browser available
Capture unavailable
```

rather than:

```text
Application unavailable
```

## 53.2 Tab Creation

Every tab receives a stable internal identity.

Required conceptual identity:

```text
TahoTabId
GeckoSessionId
GeckoViewSession
WebExtensionTabId
CaptureSessionId
```

The implementation may use different class names, but the relationships must remain explicit.

A tab must not be identified solely by its UI index.

## 53.3 Tab Switching

Switching the visible tab changes presentation only.

It must not change ownership of previously captured network events.

Example:

```text
Tab A
 └─ POST /api/login

User switches to Tab B

Tab A
 └─ GET /api/profile
```

The GET request remains associated with Tab A even while Tab B is visible.

## 53.4 Tab Closure

When a tab closes:

- in-flight capture events must reach a defined terminal state,
- persisted capture records must remain available if the user chose persistence,
- the WebExtension/native mapping must be removed,
- temporary transfer files associated with the tab must be cleaned,
- UI references must be released.

# 64. Intent Security

4. Validate version.
5. Validate payload size.
6. Validate URL syntax.
7. Validate method.
8. Validate headers.
9. Validate body metadata.
10. Validate completeness metadata.
11. Validate secret policy.
12. Create the internal request only after successful validation.

# 65. Large Transfer Lifecycle

The large-payload path should behave as follows:

```text
1. User selects Send to Taho
2. Browser calculates transfer size
3. Size is within direct threshold?
      ├─ Yes → direct Intent
      └─ No  → URI transfer
4. Browser creates temporary encrypted artifact
5. Browser grants read access only to Taho
6. Browser sends explicit Intent
7. Taho reads artifact
8. Taho validates artifact
9. Taho imports request
10. Browser receives/records completion
11. Temporary artifact is deleted
```

If Taho never reads the artifact, cleanup must still occur.

A periodic cleanup process should remove abandoned temporary artifacts after a bounded retention period.

3. Release inactive technical UI state.

5. Restore capture history from persistent storage.

Do not keep unlimited response bodies in memory.

# 96. Security Threat Model

The integration should explicitly consider:

### Threat: Malicious webpage

A webpage may attempt to cause unintended transfer.

Mitigation:

- no automatic transfer,
- explicit user action,
- native UI confirmation,
- origin/provenance display.

### Threat: Malicious Intent

Another application may send crafted transfer data to Taho.

Mitigation:

- schema validation,
- strict size limits,
- URL validation,
- no automatic execution,
- safe parsing.

### Threat: Credential leakage

Mitigation:

- default parameterization,
- masking,
- explicit secret transfer,
- no raw logs,
- secure temporary files.

### Threat: Destination substitution

Mitigation:

- original destination retained,
- high-risk warning when executing against a changed origin.

### Threat: Temporary file leakage

Mitigation:

# 116. Import Validation Limits

Taho should define maximum values for:

- number of headers,
- URL length,
- body size,
- number of query parameters,
- number of multipart parts,
- metadata depth,
- string length.

Limits prevent malformed or hostile payloads from consuming excessive memory.

---

# 117. URL Validation

Taho should validate:

- supported schemes,
- host syntax,
- port,
- path length,
- query encoding.

The Browser may capture HTTP/HTTPS URLs, but Taho must not assume that every imported scheme is executable as an HTTP request.

---

# 118. Header Validation

The import layer should validate:

- header name syntax,
- value length,
- duplicate header policy,
- forbidden transport headers,
- newline/control characters.

Headers must not permit request-smuggling-like malformed representations to pass into the execution layer.

---

# 119. Body Validation

The import layer should verify:

```text
declared size
actual size
content type
encoding
representation
```

A payload that claims:

```text
size = 2 MB
```

but contains:

```text
200 MB
```

must be rejected or streamed safely.

---


The imported request should not automatically create a new collection.

```text

Keep unresolved
```

This avoids creating duplicate environment variables for repeated imports.

---

# 122. Security Analysis Integration

After import, the user may invoke Taho's security engine.

The Browser does not need to duplicate all Taho security analysis.

The division is:

```text
Browser
→ observe and contextualize

Taho
→ test and analyze
```

This avoids duplicate product surfaces.

---

# 123. Request Execution Boundary

Import does not equal execution.

Required:

```text
Import
≠
Execute
```

The user must explicitly press Taho's normal execute action.

This protects against:

- accidental network requests,
- imported malicious payloads,
- unexpected credential transmission,
- destructive APIs.

---

# 124. Destructive Request Warning

If Taho recognizes an imported request as potentially destructive based on method/path/user configuration, it may use its normal execution warning.

The Browser should not attempt to invent a second destructive-action framework.

# 135. MVP Definition

The MVP is successful when a user can:

1. Open a website.
2. Interact normally.
3. Cause an API request.
4. See that relevant request surfaced.
5. Inspect it.
6. Tap `Send to Taho`.

8. Confirm.
9. Taho opens automatically.
10. The request appears in the Taho editor.
11. The user can edit it.
12. The user can explicitly execute it.

# 140. Final PRD Decision

The integration must be designed as a **native mobile handoff**, not as a generic export mechanism.

The ideal interaction is:

```text
Observe
  ↓
Recognize
  ↓
Inspect
  ↓
Protect
  ↓
Send
  ↓
Open
  ↓
Test
```

There should be no unnecessary intermediate representation.

The user should not need to understand:

- GeckoView,
- WebExtensions,
- native messaging,
- Android Binder,
- content URIs,
- schema versions,
- Room,
- cryptographic storage.

Those are implementation details.

The product should expose one simple mental model:

> **I found the request in the browser. I sent it to Taho. Now I can test it.**

No known cross-tab attribution defect.

A captured request can become the equivalent normalized Taho request.

- local,
- fast,
- secure,
- reversible,
